# BalloonPredictor v1.5.2

The shared Linux service stores each signed-in person's downloads, model cache,
terrain, predictions, NetCDF exports and job log in:

```text
/data1/tim/BP_Data/<verified Unix username>/
```

The username comes from the authenticated SSH account. One server process serves
all the workspaces. It does not accept a username supplied in a URL, HTTP header
or request body. The workspaces have separate job lists and file catalogues; a
person cannot open another account's predictions or exports through the API.
The service account owns the private workspace directories. Do not chmod the
individual directories to 777.

## Start the shared server

Use Python 3.12 or newer, for example your current Conda environment. Stop the
old server first. From the v1.5.2 source directory:

```bash
bash start-shared-server.sh --port 8004
```

This creates the service's virtual environment, pip cache, temporary directory
and startup log under `/data1/tim/BP_Data/.server-8004/`. It copies and verifies
the operator's existing data into their new username folder, updates internal
paths in saved predictions and writes the shared-server configuration there.
The original files are retained. The copy can take several minutes.
The previous common workspace is imported into the operator's username folder.
Other accounts start with their own weather downloads and results; configured
external ERA5/WRF archives remain available to all of them for reading.

If your previous installation used a custom configuration or data folder:

```bash
bash start-shared-server.sh --port 8004 \
  --config /path/to/your/previous/config.yml \
  --source /path/to/your/previous/data
```

The script detects `data_dir` from the old configuration when supplied, otherwise
uses the old `~/.local/share/balloon-predictor` folder. External ERA5 and WRF archive
paths are retained. A repeated launch uses the existing server configuration and
does not overwrite migrated files. If you already use the destination and want
to retain it without importing old files, use `--fresh`.

On subsequent starts run the same command. To use another mount, add
`--shared-root /path/to/BP_Data`. All SSH accounts need directory traversal access
to the mount and its parent directories. Where the operator owns a world-writable
`BP_Data` directory, the launcher adds its sticky bit (1777), retaining write
access while preventing other accounts from renaming each other's directories.

The default bind address is 0.0.0.0. Use this behind the intended VPN/network
access controls. Add `--host 127.0.0.1` if access should be through SSH tunnels only.
No new public port is required beyond the existing BalloonPredictor port.

After confirming the new data and exports work, the operator can remove their
old home-directory copy to recover that quota. The migration does not delete it.

## Connect

In Android, Windows, macOS or the Debian desktop app, choose the large **Server**
button, choose **SSH tunnel**, then enter the server, your own SSH username and
the BalloonPredictor port (8004 in this example). Turn on your VPN first where
needed. SSH still handles passwords, host fingerprints and sign-in challenges;
the app does not store passwords. Reconnect with v1.5.2 to use the new personal
workspace handoff. Older apps cannot sign into a shared v1.5.2 service.

The Linux server uses its kernel's Unix-socket peer credentials to verify the
account behind the SSH command. A one-use 60-second sign-in ticket becomes an
HttpOnly session cookie; it is not logged in a URL path. Restarting the service
invalidates its browser sessions. Choose Server and reconnect if a session expires.

For a normal browser, log into the server through SSH and, from the source
directory, run:

```bash
python -m balloon_predictor.login --port 8004
```

Open the returned sign-in link while on the VPN, replacing 127.0.0.1 and the
port with your forwarded or VPN-accessible address as appropriate. Generate a
new link if the 60 seconds have elapsed. This extra sign-in is necessary for
private user folders; an anonymous connection has no verified username.

Choose **Local** to run on the device instead. Desktop apps keep the full local
engine. Android retains its offline forecast-pack calculator; it does not bundle
the Python/NetCDF stack. Save a .bpforecast file while connected, then open it
in Local mode before heading somewhere without a signal.

## Interface and errors

- Two large Local/Server buttons appear first on every installed app.
- Android has one header with the balloon logo, version, Weather and Server
  actions. Returning from Server settings retains the active WebView and flight.
- Rescan requests use JSON and are exercised through authenticated SSH in the
  Android emulator. Network failures now explain that the VPN/tunnel or server
  may be unavailable, rather than displaying only “Failed to fetch”.
- Disk-full, quota, read-only and permission failures include the active data
  directory and OS error number. Storage health remains readable when a new
  storage lease cannot be created.
- Manage weather shows the selected username, data path, log path, write check
  and filesystem free space. Filesystem free space does not measure an
  account-specific quota; the write check also catches quota failures.

A full home quota could explain failed result writes and interrupted IFS
downloads. The old logs omitted errno, so they do not prove that diagnosis.
**MissingTerrainError** means no valid physical DEM pixel was available; moving
files cannot supply missing tiles. Retained tiles move with the data. Use the
existing missing-tile download action for any additional launch/descent tiles.
A changed ERA5 topography receipt still requires a rescan; this is separate from
storage space.

Per-user job log:
`/data1/tim/BP_Data/<username>/logs/balloon-predictor.log`.
Service startup/output log:
`/data1/tim/BP_Data/.server-8004/server.log`.

An explicit `BP_DATA_DIR` or `data_dir` still overrides the standalone default.
On Linux with the specified shared mount present and no explicit data-folder override, a normally started server
automatically enables the shared workspace service unless `shared_server: false`
is explicit. Other machines use their normal per-user app-data folders. Local
desktop folder selection remains available in Manage weather; the shared
service's root is managed centrally by its operator.

## Installers and validation

The v1.5.2 test branch runs Python/browser tests and the existing installed-app
checks on Windows x64, both Apple silicon and Intel Macs (macOS 15+), Debian 12+
amd64, and Android 8+ in an emulator. The Android test now includes personal SSH
sign-in, the rescan, the condensed header, session return paths and an offline
flight. Installer files are available from the successful Actions artifacts.

The release script checks all five workflow results for the same source commit,
checks each binary's checksum and source-commit metadata, collects both Mac
installed-app reports, and archives that exact source. It creates a draft by
default. `--publish` fast-forwards main and publishes only after those checks.

Android needs a stable signing key for normal upgrades even when distributed
directly as an APK; no Google Play account is needed. The optional
`setup-android-signing.sh` retains an existing repository key or generates a
private one and configures GitHub secrets before the next build. Back it up
privately. Previously installed APKs made with temporary test keys may need to
be uninstalled once before installing the stable-key build; export important
setups and keep forecast packs first.

Windows and Mac signing/notarization status is unchanged from the previous
installers. Native installed-app tests must pass in Actions before a release;
compilation alone is not treated as an installed-app test.

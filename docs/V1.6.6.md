# BalloonPredictor v1.6.6

Default server port: **8011**.

## Faster native WRF predictions

Predictions now keep up to three required WRF files open for the calculation, including sensitivity members, launch series and coordinated arrivals. The reader caches nearby three-dimensional blocks with all original mass levels, staggered-face averaging, earth-relative winds, temperature and humidity. Blocks share the existing `cache_mb` byte limit, and explicit HDF5 variable caches are bounded separately to 24 MiB across the three retained handles. NetCDF operations still use the existing process lock. Every handle closes after success, failure or cancellation; there is no multicore/process-pool change.

The horizontal grid, vertical levels, integration timestep, interpolation, physics, sensitivity seed and coverage rules are preserved. The scalar reader remains the reference for automated equivalence tests and non-prediction paths. ERA5, IFS and GFS prediction readers retain their existing behavior. Initial WRF grid setup still takes place when a run is first opened; this update addresses repeated forecast reads during the flight.

No new cache files or once-off conversion are required. The improvement reuses bounded memory while working with your existing files. No timing exercise is required from you. Automated tests cover unchanged native values and trajectories, missing data, humidity/surface anchors, wind rotation, source changes, cache limits, retained-handle reuse, old NetCDF formats and cleanup.

## Vertical velocity and wind animation

Weather field now includes **Vertical velocity · m/s** when the selected flight's dataset supplies it; otherwise **Vertical velocity (unavailable)** is disabled. Native WRF uses its destaggered `W` field. Normalized forecasts use their existing vertical velocity in m/s, including the existing conversion from pressure velocity where supplied by the adapter. Missing vertical velocity is never invented as zero; unavailable cells are transparent, and a layer with no valid values reports an explanation. Positive values indicate rising air and negative values sinking air.

Both altitude and model-pressure views support this layer, with a diverging colour scale and the compact map key. Animated particles continue to display the **horizontal** wind. Their visual speed receives a smooth, bounded boost at wider zoom so movement remains easier to see; stored wind values and trajectory calculations are unaffected.

## Comparing models at one launch point

Open **+ → Add a launch** and select a **Weather model**, then its **Run / saved forecast** where relevant. Choose the launch date/time and calculate. The earlier tracks stay in place, including when comparing different models at the same valid time. The date/time heading sits above its editable boxes, with a consistent calendar picker on desktop and phones.

Each launch retains its own dataset, forecast cycle, physics request, source receipts and sampled profile. Its weather overlay, profile, selected-flight export and map coverage follow that launch. Selecting a model without atmospheric vertical velocity disables an inherited vertical-wind flight setting for that added launch, with a notice before calculation. Other flight settings are inherited from the launch-point setup; the complete new flight must fit the selected model's actual coverage.

Launch buttons include the year and source, for example **2026-11-26 06:00 UTC · WRF** and **2026-11-26 06:00 UTC · IFS**. Hover for the dataset/run details. Selected-flight `.bpflight` files include that launch's own setup and model; saving all open launches preserves the mixed comparison. Mixed-model CSV exports identify the dataset, source and forecast initialization; GeoJSON features and KML folders retain each launch’s source metadata. The main Flight Setup remains the launch point's starting setup; selecting a comparison does not overwrite the other tracks.

## WRF weather maps

Native WRF overlays now read larger contiguous tiles with one retained file handle per frame. Only the core fields and vertical levels needed for the requested altitude or pressure are read; unusual or missing columns use complete core columns to preserve coverage masks. Prepared two-dimensional tiles share the existing byte-bounded memory cache. Reopening a layer or panning across already prepared tiles can reuse it.

The map reads the visible area plus a panning buffer. Its raster follows the viewport and native grid spacing, up to 262,144 output cells (at most 1,024 on either axis). Near zoom can show approximately the native 1 km detail; far zoom samples a coarser native lattice to keep the map responsive. The raster's decoded floats are transferred compactly. Time interpolation, WRF destaggering/earth-relative rotation, and model-derived height/pressure remain in use. Missing layers and unavailable areas stay transparent. Native WRF **trajectory calculations keep their original grid and sampler**. ERA5, IFS, GFS and imported normalized datasets retain their existing weather-overlay readers and default 40 × 40 raster.

A compact colour key appears beside the Ascent/Descent map legend whenever weather is shown. It follows the chosen field and colour limits. Beside **Animated wind**, a white/black switch changes arrow contrast without requesting weather again. Tracks remain above the overlay.

## Reconnect without losing flights

The apps keep the flight page and its local address alive when SSH drops. Small
SSH keepalive messages run every 20–25 seconds. A disconnected transport retries
with a bounded delay. A reusable password may stay in memory until the app quits;
it is never written to the connection preferences. One-time codes are not cached.
If a new sign-in is needed, the app waits until an action needs the server before
asking. Completed tracks, the selected launch, and the map remain in place.

The Server indicator is green when connected, orange while reconnecting, and red
when sign-in is required. A normal browser also keeps its page through an expired
server session and asks for credentials in place. It uses your existing network
connection; the browser itself does not create a VPN or SSH tunnel.

If the VPN is off, turn it on. Keepalive/retry cannot start or repair the VPN,
restart a stopped server, or prevent Android from suspending a background app.
A server restart can end an unfinished calculation; completed saved results remain.
Prediction submission retries use an identifier to avoid starting the same job twice.

## Save and reopen calculated flights

Flight Details contains:

- **+**: open the launch menu, with **Add a launch**, **Open saved flights** and **Recent flights**. Add a launch retains the existing tracks, including after failed calculations. The dialog shows the available weather window; the complete flight must fit within it.
- **↓** beside each completed launch: save that launch for reopening.
- **×** beside any launch: remove it after confirmation, including an unavailable launch. Other launches remain.
- A dark **Save flight(s)** card: download the selected launch or all open launches. Its two NetCDF cards fill the same width below it; on phones they stack.

Use **Cancel calculation** in Flight Setup, the status banner, or the launch dialog to leave a stalled calculation. The interface releases immediately so saved results can be opened. A reachable server cancels queued work or stops running work at the next integration/read checkpoint. If disconnected, a message explains that server cancellation could not be confirmed. Late results never replace the newly opened workspace.

Saved-file names begin with the UTC download time, followed by the model/domain, forecast initialization, launch valid time or range, sensitivity member range and launch-point name(s). For example:

```text
20261126_182030_WRF-D02_INIT-20261124_120000Z_VALID-20261126_060000Z_S00-S50_Llanbedr.bpflight
```

`S00` is the nominal flight. `S00-S50` includes the nominal flight and up to 50 requested sensitivity members; failed members are still described in the saved results. A multi-launch download uses the earliest/latest launch UTC times. Distinct model names and initialization times are retained (multiple cycles use a list or earliest/latest range). `INIT-NA` means no forecast initialization was recorded, as with ERA5 or Demo; the app does not invent one. Names are shortened and stripped of unsafe filename characters for desktop and Android downloads. Older `.bpflight` files remain compatible for viewing. New files preserve nanosecond source timestamps as exact text, avoiding browser number rounding that could falsely reject a later weather/export request. Very old files whose timestamps were already rounded may need a recalculation for newly sampled exports; their stored tracks still reopen.

A `.bpflight` file includes setups, tracks, sensitivity members, sampled profiles,
and source metadata. It contains **no weather grids**. Opening it does not run the
trajectory calculation or fetch weather. Weather overlays and newly sampled
NetCDF exports require a connection to the original weather source, requested
through the usual controls. Source receipts are checked before re-sampling;
removed or changed source data is reported rather than silently substituted.

The current workspace is saved automatically after changes. Up to eight recent
snapshots are retained within a 32 MB local history limit. In an SSH app this
history is a local file under the app's data directory, separated by server and
username, so a different local tunnel port on restart does not hide it. Browser
and local desktop sessions use the browser/WebView's IndexedDB storage, separated
by server origin and signed-in user. Clearing app/browser storage removes local
history; keep downloaded `.bpflight` files for long-term copies. A storage failure
shows a message beside the flight controls. The existing setup-only JSON and
`.bpforecast` weather packs remain separate formats.

Android Local continues to calculate from `.bpforecast` weather packs. Its
bundled land/coastline map, coordinate grid, regional labels and forecast boundary
are visible as soon as a pack opens. Android Local also opens and saves `.bpflight` tracks and restores its last locally
saved flights. Select a saved launch to view its map. Its small offline viewer
shows tracks/endpoints; the full profile and window tools remain in the dashboard.
A new offline calculation still needs a `.bpforecast` pack. Offline-generated
tracks have no original server source receipts; recalculate on the server for
newly sampled NetCDF exports.

## Shared weather

On your server, keep personal workspaces in:

```text
/data1/tim/BP_Data/<username>/
```

The app also scans these common folders, read-only, for every signed-in user:

```text
/data1/tim/BP_Data/wrf/
/data1/tim/BP_Data/ifs/
/data1/tim/BP_Data/gfs/
```

Create them as the server operator:

```bash
mkdir -p /data1/tim/BP_Data/{wrf,ifs,gfs}
chmod 755 /data1/tim/BP_Data/{wrf,ifs,gfs}
```

The app needs read and directory-traversal access, not world-write access. Grant
your ingestion account write access as appropriate. App cleanup and personal
weather downloads operate on personal folders and do not modify common files.
The names `wrf`, `ifs`, and `gfs` are reserved and cannot also be workspace usernames.

Put **converted `wrfout*` NetCDF files** directly in `wrf`, or in run/domain
subfolders. Copy to a name ending `.part` and rename after the copy finishes.
Click **Manage weather → Rescan local data** in each already-open workspace;
newly opened workspaces scan automatically. One run can contain multiple frames.
Keep different nests/runs separate; overlapping duplicate times are reported.

The supplied SkySight format is supported: staggered U/V/W, total P and PH with
zero PB/PHB, and T = potential temperature minus 300 K. `parent_cycle_utc` groups
frames into the forecast cycle, even when each frame has a different
`SIMULATION_START_DATE`. Large WRF volumes stay on disk; sampling reads columns.

If COSALPHA/SINALPHA are absent, Lambert rotation is derived from MAP_PROJ=1,
TRUELAT1, TRUELAT2 and STAND_LON, using the NCAR WRF wind convention. The supplied
temperature diagnostic supports the standard temperature conversion. Its wind
metadata does **not** establish whether the converter already rotated the winds.
The default is grid-relative WRF winds. If the converter's author confirms they
are already east/north, set this in the server configuration and restart:

```yaml
wrf_wind_reference: earth
```

Use `grid` for the normal WRF convention, or omit the setting. A per-file global
attribute `balloon_wind_reference` is also understood when no configuration
override is set. Sampling, weather overlays and model-box exports use the same
rotation. Other projections without rotation fields are reported as unsupported.
The raw SkySight archive `.h5` schema has not been supplied; use the converted
NetCDF files, not the raw archives.

For `ifs` and `gfs`, copy **BalloonPredictor normalized NetCDF** datasets (the
processed `.nc` files from a weather library). No JSON sidecar is required. They
are read lazily and must declare earth-relative winds and AMSL heights. Raw GRIB
and other NetCDF formats must first be imported with `import-ifs` or `import-gfs`;
the app does not guess their units or silently interpret model-level GRIB as
pressure-level data. Model-level IFS needs an appropriate converter first.

For example, to normalize pressure-level GRIB into a staging directory on the
large data volume, in your server environment:

```bash
BP_DATA_DIR=/data1/tim/BP_Data/.forecast-import \
  python -m balloon_predictor import-ifs --name ifs-20261126-00 \
  --files '/path/to/ifs-pressure-level-files/*.grib2'
cp /data1/tim/BP_Data/.forecast-import/weather/ifs-20261126-00.nc \
   /data1/tim/BP_Data/ifs/ifs-20261126-00.nc.part
mv /data1/tim/BP_Data/ifs/ifs-20261126-00.nc.part \
   /data1/tim/BP_Data/ifs/ifs-20261126-00.nc
```

Include the required winds, temperature and geopotential/height. Use `import-gfs`
for GFS. The ordinary online IFS/GFS download controls remain available and save
private datasets as before.

## Run the browser server

From the extracted `balloon-predictor-v1.6.6` source directory, with Python 3.12+
available:

```bash
bash start-shared-server.sh --port 8011
```

Then use port 8011 in the browser or app's Server settings. Existing versions can
continue on other ports. Check custom paths in your server configuration; the
new source does not copy or delete shared model files.

## Prepare installers and release

Extract the kit beside your normal Git checkout. From **inside that checkout**:

```bash
bash ../balloon-predictor-v1.6.6-kit/prepare-v1.6.6.sh
```

This creates/updates `release-v1.6.6-test` using a temporary checkout and starts
five GitHub workflows. Your working checkout and `main` stay untouched. Wait for
Python/browser, Windows, macOS, Android and Debian to pass **on that same commit**.
Hosted runner allocation errors require rerunning the affected workflow.

Use the stable Android signing key already in the repository's GitHub secrets.
There is no Google Play requirement. If you need to configure signing, run the
kit's `setup-android-signing.sh` on your local GitHub machine, then prepare with
`--retest`. Keep a backup of the same signing key for future app updates.

Collect the installers and create a draft release:

```bash
bash ../balloon-predictor-v1.6.6-kit/release-v1.6.6.sh
```

The default output is `~/balloon-predictor-releases/v1.6.6/<commit>/` and contains
Windows `.exe`, universal macOS `.dmg`, Android `.apk`, Debian `.deb`, source ZIP,
checksums and build reports. Interrupted downloads retry into a temporary folder;
only complete verified artifacts are reused. A draft does not advance `main`.

After reviewing the draft, publish and fast-forward `main`:

```bash
bash ../balloon-predictor-v1.6.6-kit/release-v1.6.6.sh --publish
```

`--check-only` only collects/verifies files. `--allow-test-apk` allows a temporary
Android key for a test draft; publishing requires the stable release key. The
release helper never uses successful workflows from an older commit.

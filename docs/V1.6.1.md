# BalloonPredictor v1.6.1

This update fixes map-request identification and adds a Weather panel for the
currently selected flight. All v1.6 features remain: zoomable Skew-T and winds,
coordinated docking, launch-move confirmation, grouped weather runs and aligned
Local/Server connection cards. The shared server still uses **port 8005** and
`/data1/tim/BP_Data/<verified Unix username>/`.

## Weather on the flight map

Calculate a flight, then click **Open Weather** next to **Open Flight Profile ·
Skew-T & winds** in Flight Details. **Weather** also appears beside Map, Details
and Profile in the Trajectory toolbar (inside More when space is limited).

The overlay follows the **bold, selected flight**, including its launch point
and selected time in a series or coordinated plan. It uses that saved
calculation's exact dataset ID, not the current weather-selection form or the
latest forecast from a download service. Its height is the nominal flight's
**target or burst altitude, in metres AMSL**. The default weather time is the
selected flight's **launch time**. An optional time selector shows the weather
when that flight reaches its target/burst instead. Both the height and exact
UTC weather time are displayed explicitly.

Choose temperature (°C), eastward u, northward v or wind speed (m/s). Opacity
changes the colour field; **Animated wind** adds flowing particles from the same
sampled u/v. The animation illustrates direction and relative speed at a fixed
weather time, accelerated for visibility. It does not advance the forecast or
represent the balloon's trajectory. Reduced-motion preferences start it off.
Hide the weather without clearing the calculation, or minimise its controls
while keeping the map overlay. Tracks, sensitivity outlines and launch markers
remain above the weather; weather layers do not intercept map gestures.

The default **Flight area** includes the nominal and sensitivity tracks with a
margin of at least 0.5° or 50 km, clipped to available model coverage. **Load
visible map** samples the current map view on demand. Panning/zooming keeps the
existing geographic field in place; it does not repeatedly download weather.
The default grid is 32 × 32 samples. The coloured display interpolates those
samples; it does not add resolution to the source model.

All four fields are loaded together and reused when changing fields or opacity.
A small browser-memory cache also reuses recent selections. Changing the bold
flight clears the previous image immediately and loads its weather. Delayed
responses from an earlier selection cannot overwrite the current one. Editing
or removing the calculation clears its weather. Wind rendering pauses while
the map or browser tab is hidden.

Missing model cells, unsupported height/time coverage and gaps in atmospheric
layers are never replaced with zero or another forecast. Missing regions stay
transparent; an entirely unavailable area gives an actionable message. The
saved flight's near-surface estimation policy is preserved and any estimated
grid points are labelled. Original source-file receipts are checked before and
after sampling. Changed/deleted input files require a new prediction.

Native ERA5 and WRF columns are loaded in bounded blocks, then use the same
horizontal/time/vertical interpolation and earth-relative winds as prediction.
There is no separate model download for this view. It is available in the
browser and full flight workspace on Windows, macOS, Debian and server-connected
Android. Android's separate basic offline calculator keeps its existing feature
set and saved-forecast/coastline operation.

The fourth panel can float, maximise, minimise, lock or share a docking layout.
Half/quarter arrangements now include every open, unlocked panel; their shared
dividers remain adjustable. Saved three-panel layouts remain compatible.

## OpenStreetMap requests

The shared server deliberately uses a restrictive document referrer policy to
protect sign-in/session information. Map images now explicitly send only their
**origin** as the referrer, overriding that policy for tile images without
sending a page path, query string or token. Installed WebViews retain their real
browser identity and append BalloonPredictor's version and project contact URL.
The visible attribution reads **© OpenStreetMap contributors**.

Tiles keep the normal browser HTTP cache. Requests use the standard HTTPS tile
endpoint, wait until map motion settles and retain a modest buffer. There is no
cache-busting query, no forced re-download, no bulk/offline OSM tile downloader,
and no proxy or alternative hostname to evade a block. Installed-app CI blocks
external images; browser tests fulfil synthetic tiles locally and verify the
actual outgoing referrer under the shared server's restrictive policy.

Restart the updated server and reload its browser page. Install the newly built
apps for their WebView identification change. This fixes the observed request
policy defect; it cannot promise that an existing network/IP block is lifted
immediately or that the volunteer service has unlimited capacity. If a block
persists with the updated app, report the compliant request details through
OSM's linked block page or configure a suitable hosted map service as a future
change. The weather and flight calculations do not depend on basemap tiles.

Official references: [OSM tile policy](https://operations.osmfoundation.org/policies/tiles/)
and [Leaflet 1.9.4 tile options](https://leafletjs.com/reference-1.9.4.html#tilelayer-referrerpolicy).

## API

`POST /api/predictions/{prediction_job_id}/weather-overlay` accepts:

```json
{"flight_index": 0, "time_basis": "launch", "area": null, "grid_size": 32}
```

It returns an asynchronous job ID, polled at `/api/jobs/{job_id}`. `time_basis`
is `launch` or `target`. Optional area order is `[north, west, south, east]`;
longitudes can continue across the date line, latitude is limited to ±85° and
grid size is 8–48. Dataset, altitude and UTC time are derived from the completed
saved flight and cannot be substituted in the request. The result contains all
four fields, coordinates, masks, units in field names/metadata, time, height,
source identification and warnings. Overlay jobs remain in memory and do not
create persistent download files. Existing per-account job isolation applies.

## Validation and installers

The kit's `VALIDATION.json` lists completed local checks and their limits.
Regression tests cover synthetic/normalized forecasts, native ERA5 and rotated
WRF, source changes, coverage masks, date-line bounds, request limits, selected
series members and separate account stores. Real Chromium checks cover map
request headers, colour fields, opacity, wind pixels, caching, stale responses,
viewport sampling, four-panel docking, mobile controls and animation lifecycle.

Prepare the **release-v1.6.1-test** branch using the kit script from your usual
Git checkout. It can update a prepared v1.6 branch or apply the full changes from
the existing v1.5.3 source. It preserves your checkout and does not update main.
Wait for all five workflows on that exact new commit before running release.
Old successful installer runs cannot certify new code. The release script
collects the Windows EXE, universal Mac DMG, Android APK, Debian DEB and source
ZIP, and creates a draft by default. `--publish` publishes the tested version
and advances main without forcing it. Native installation/emulator tests must
run on GitHub; they are not represented by local compilation or browser tests.

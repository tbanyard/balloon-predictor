# BalloonPredictor v1.6.2

This update expands automatic weather coverage, adds the ERA5 viewer's colour
range controls and selectable altitude/pressure, increases confirmed download
windows to 144 hours, and makes the flight-status banner dismissible. The
shared-server default and new server-connection forms now use **port 8007**.
All previous flight, profile, export, storage and sign-in features remain.

## Weather coverage and controls

**Open Weather** in Flight Details, or the **Weather** tab, still follows the
bold, selected flight and its saved dataset/time. The default vertical level is
that flight's target/burst altitude. The Weather header now has just its title,
with Lock/Arrange controls on the same row. The white weather-information box
has been removed from the map. Its colour bar, units, height and UTC time remain
in the Weather panel.

Regional models fill their **whole available model box**, matching their dashed
coverage boundary. The old track-sized box, Flight area button and Load visible
map button are gone. Weather outside the actual dataset is not invented.

Large/global datasets use the **visible map plus a panning buffer**, clipped to
available data. Panning inside that buffer reuses the existing weather; moving
beyond it loads the next area automatically after a short debounce. Zooming
well into a coarse loaded area also refreshes its sampling. This samples the
already available saved forecast, not a new remote download. At most two overlay
loads are active in a browser; newer flight/level/time selections take priority
and outdated responses cannot overwrite them. Missing cells remain transparent.

The default display grid is 40 × 40 samples. Colours interpolate this grid;
they do not increase the model's native resolution. Tracks and markers remain
above the weather, and the weather layers do not intercept map gestures.
Animated wind uses the same earth-relative u/v data at a fixed weather time;
it pauses when the map or browser tab is hidden.

### Colour range

The attached ERA5 viewer's three choices are available under **Colour range**:

- **Auto · full layer** uses the 2nd–98th percentiles of the loaded field, with
  rounded limits. Automatic u/v limits are symmetric around zero.
- **Auto · visible window** samples visible map values and updates the limits
  after pan/zoom. This recolours existing data without another model request
  while its coverage remains sufficient.
- **Fixed limits** preserves the chosen minimum/maximum across flights, times,
  levels and panning. Editing either bound selects this mode. Settings are
  remembered separately for each weather field during the session.

An invalid range keeps the previous valid colours and gives an inline message.
If the visible window has no represented values, automatic scaling explicitly
falls back to the loaded layer's limits. The colour bar stays in this panel.

### Altitude or pressure

Choose **Flight target / burst altitude**, **Altitude · m AMSL**, or **Pressure ·
hPa**. Changing this display level does not change the calculated flight. Custom
altitudes can be entered from −500 to 100,000 m, but values are shown only where
that source actually represents the requested level. The prediction's existing
55 km flight limit is unchanged. Pressure requests must be above 0 and at most
1100 hPa; available model levels still determine usable coverage.

Altitude fields retain the saved flight's interpolation and labelled
near-surface-estimation policy. Pressure fields use **actual native model
pressure**, interpolating adjacent represented levels in log pressure before
horizontal/time interpolation. They do not convert hPa to an ISA height. The
panel shows the resulting model-height range. Below-ground pressures, missing
layers and unrepresented top/bottom levels stay transparent. No pressure
extrapolation or near-surface estimate is introduced. A dataset without terrain
and surface pressure is explicitly identified as unable to identify additional
below-ground values beyond its supplied missing-data mask.

Source receipts are checked before and after sampling. Deleted/replaced inputs
require a new prediction before another sample can be made. No alternate model
or forecast cycle is silently substituted.

## Download area and duration

Previously, opening Manage Weather used the fixed UK box **60, −12, 48, 5**.
The flight's online-download shortcut instead used launch ±5° latitude and ±8°
longitude. Both GUI entry points now start from the current launch, with **5°
additional padding on every edge of the old shortcut**: ±10° latitude and ±13°
longitude, clipped at the poles/date-line edge supported by the downloader.
The bounds remain editable. Reopening for the same launch preserves manual
edits; **Reset to launch area** restores the defaults. Moving to another launch
initialises its own bounds. API calls without an area, which have no launch
coordinates to use, retain a broader fixed fallback of **65, −17, 43, 10**.

Downloads can cover **up to 144 hours**. A window over 72 hours shows a short
notice and asks for confirmation before any download is submitted. Cancel
starts nothing. Up to and including 72 hours requires no extra confirmation;
over 144 hours is rejected. Forecast-cycle availability, source cadence,
remaining disk space and `max_weather_mb` still apply. Larger selections may
need a smaller area or coarser ERA5 grid to fit the configured memory limit.

For API callers, requests longer than 72 hours must include
`"confirm_large_download": true`. This flag acknowledges the longer request;
it does not bypass the 144-hour, coverage or resource limits.

## Completed-flight banner

The orange status strip has a right-hand **×** once calculation finishes.
Dismissal removes the strip and the panels expand into the freed space. A new
calculation or changed flight status shows it again. The close button is hidden
while calculation is running, and the main Flight Setup status remains available.
Weather loading/panning does not reopen a dismissed flight banner.

## Server and apps

Use **8007** for this version:

```bash
bash start-shared-server.sh --port 8007
```

Open `http://YOUR-SERVER:8007`. The previous version on 8006 can remain available
for comparison. The new shared-server state is in `.server-8007`; personal data
stays in `/data1/tim/BP_Data/<verified Unix username>/`. Do not delete or copy
those model/download folders to change ports.

New Android/Windows/Mac connection forms default to 8007. Existing saved
connections keep their explicit port: set it to 8007 when connecting an updated
app to this new service. Windows/Mac/Debian still support running the full
engine locally. Private internal app-loopback ports remain managed by the apps.

### Android local operation

The existing **Local** choice already performs flight calculations entirely on
the phone from a saved **.bpforecast** file, including without signal or VPN.
In the full workspace, calculate a flight with downloaded IFS/GFS or a
pressure-level ERA5 dataset, then use **Save offline forecast for Android** in
Flight Details. Copy that `.bpforecast` file to the phone. Choose **Local** and
**Open saved forecast**, and check its displayed area/time/height coverage before
going offline. Direct native ERA5/WRF archives need a supported exported pack;
the phone does not read their NetCDF/GRIB/GeoTIFF files directly. This release retains that
working path, CSV/GeoJSON export and the offline coastline map; there is no
unannounced network dependency added to its calculator.

Running the full desktop/server engine on Android is possible as a dedicated
port, but it is not a matter of allowing a larger APK. The current Java APK does
not embed Python or Android builds of the scientific C libraries used by
NumPy/SciPy, netCDF4/HDF5, rasterio/GDAL and ecCodes. They would need compatible
Android builds, file-picker/storage integration and actual ARM64/emulator tests.
Desktop/Linux wheels cannot simply be bundled into the phone app. v1.6.2
therefore keeps `.bpforecast` local operation and the full server-connected
workspace; it does not claim a newly tested full offline Python engine.

References: [CPython on Android](https://docs.python.org/3/using/android.html),
[building Python packages for Android](https://docs.python.org/3/using/android.html#building-a-python-package-for-android)
and [Chaquopy package guidance](https://www.chaquo.com/chaquopy/doc/current/faq.html).

## Overlay API

`POST /api/predictions/{prediction_job_id}/weather-overlay` still returns a job
polled at `/api/jobs/{job_id}`. The GUI sends, for example:

```json
{"flight_index": 0, "time_basis": "launch", "coverage": "auto", "area": [64, -18, 42, 10], "grid_size": 40, "pressure_hpa": 500}
```

Use either optional `altitude_m` or `pressure_hpa`, never both. Omitting both
selects the saved flight's target/burst altitude. `coverage: "auto"` fills a
regional model or uses the supplied buffered viewport for a large/global model.
Explicit older API areas remain honoured with the default `coverage:
"requested"`; an omitted viewport in that compatibility mode retains the old
track-area behaviour. Area order is north/west/south/east; longitudes may
continue across the date line. Dataset and time still come from the selected
completed prediction. Grid size remains bounded at 8–48.

Results identify `coverage_mode`, `model_bounds`, `bounds`, vertical coordinate,
pressure or altitude and actual height range, as well as all four fields and
per-cell heights. Invalid cells are null, not zero. Existing per-user job
isolation and source validation apply.

## Tests and release

See the kit's `VALIDATION.json` for actual local results and their limits.
Focused tests cover full-model/global/date-line extents, custom altitude,
log-pressure/model-height interpolation, missing layers and terrain, native
ERA5/rotated WRF, request bounds, API routing and confirmed 144-hour windows.
Real Chromium tests exercise all colour modes, auto coverage, pressure/altitude,
caching/stale responses, particles, four panels, mobile controls, dismissing the
status strip and download confirmation/cancellation without external downloads.

The kit's prepare script supports the existing v1.5.3 source, v1.6.0 and v1.6.1,
including the known previous default-port change to 8006. It operates in a
temporary checkout and preserves your normal checkout. All five workflows must
pass on the exact new `release-v1.6.2-test` commit. Native installed-app/emulator
tests run on GitHub; a local compile is not represented as an installation test.
The release script downloads the four packages/source and creates a draft by
default; `--publish` publishes the tested version and advances main without
force-pushing it.

# BalloonPredictor v1.3

Run with Python 3.12 and `bash start.sh --port 8001`. If you have an activated
Conda/virtual environment, install this release's `requirements.lock.txt` first;
v1.3 adds rasterio for GeoTIFF terrain. Existing v1.2 launch setups are retained.
Window geometry uses a new storage key, so old off-screen layouts are reset.

## Coastal launches and physical terrain

The launch altitude always remains the value you enter, in metres AMSL.
Forecast heights and model orography remain unchanged. Open **Ground & model
mismatch**, choose one of these physical launch-ground sources, and click
**Check ground** to inspect the difference:

- **Known site elevation**: enter a surveyed/orthometric ground elevation. Leave
  it blank if unknown; a blank value disables the physical launch-ground check.
- **Local high-resolution DEM**: samples the finest covering valid GeoTIFF pixel.
- **Use model orography**: explicitly uses the weather model's terrain as ground.

A launch more than 1 m below the selected physical ground is rejected. A launch
below coarse model terrain is allowed under the default **near-surface bridge**
policy: each contributing spatial/time column holds its lowest valid wind and
specific humidity; temperature and pressure are extrapolated downward with a
6.5 K/km lapse rate and hydrostatic balance. This is an approximation, not new
resolved forecast air. The depth is limited to 3 km. **Strict** mode rejects
sampling below any contributing column's lowest valid air anchor, including its
10 m surface-wind anchor if supplied. Missing interior layers in native readers,
model-top limits, time gaps and horizontal coverage checks remain in force.

Results record physical/model ground, their difference, the bridge method,
maximum depth and first/last affected sample times. Sonde NetCDF carries the
same science and adds global attributes describing the approximation. Its
existing 22-variable sonde schema is preserved. Unknown station ground is NaN.
The launch coordinate is never moved vertically to make a forecast fit.

**Landing surface is a separate setting**, under Physics & sensitivity. Choose
model terrain, a known fixed AMSL altitude, or physical DEM. Choosing a known
launch-site elevation does not assume that elevation across the landing area.
For coastal flights, a physical DEM is preferable when it covers the entire
trajectory and landing area. A fixed surface is useful over known flat terrain.

## Regional DEM / DTM tiles

Manage weather shows the actual terrain directory. By default it is
`<data_dir>/terrain`; set `terrain_dir` in your configuration or `BP_TERRAIN_DIR`
to use an existing collection. Place single-band `.tif` elevation rasters there,
with a CRS, nodata, and orthometric elevations in metres. Pixel sampling uses
the native covering cell; nodata is never interpolated across a coastline.
Multiple regional/projected tiles can be used, with the finest covering pixel
preferred. Reader handles are bounded and protected for concurrent jobs.

**Download GLO-30 tile at launch point** fetches one public 1° tile from the
Copernicus public COG collection, with progress and an atomic file write. There
is no global terrain download. Add adjacent tiles when flights leave the launch
tile: move the launch marker into the neighboring tile, download it, then restore
your launch location, or copy regional tiles into the terrain folder. Missing
public tiles are reported; they are not automatically treated as sea, because
some land tiles are also unavailable.

GLO-30 is a **digital surface model**, including vegetation and buildings. A
local bare-earth DTM is preferable for launch and landing ground. GLO-30 uses
EGM2008 orthometric heights; local vertical datums can differ. The app performs
horizontal CRS conversion, not vertical-datum or GPS ellipsoid conversion.

Sources and licence:

- https://registry.opendata.aws/copernicus-dem/
- https://copernicus-dem-30m.s3.amazonaws.com/readme.html
- https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM

## Download model box NetCDF

After predicting, use **Download model box NetCDF** beside the sonde export.
Choose the selected flight (including its successful sensitivity tracks) or the
whole series/coordinated plan. Its own scope selector defaults to **full flight**;
you can also choose ascent only. The sonde's separate scope remains independent.

Each box contains:

- The native horizontal grid enclosing every selected trajectory, expanded by
  at least 0.5° or 50 km in every direction, whichever is larger. Longitude
  margins account for latitude and dateline crossing. Extra interpolation nodes
  are retained at box edges.
- All **available** model vertical levels, including levels above the sonde.
  It does not request unavailable upper-air levels from a remote service.
- Native timestamps bracketing the first launch through the last selected
  endpoint, with all intervening source timestamps.
- Earth-relative u/v, temperature, pressure, altitude, humidity and vertical
  wind where supplied, plus available surface fields and unchanged model terrain.
  ERA5 L137 exports include native model-level numbers and half-level A/B
  coefficients. WRF fields use the same destaggering, earth rotation and height
  calculations as trajectory sampling.
- Dataset/run provenance, exact source file size/mtime receipts, requested bounds,
  clipping flags, and an uncompressed-size estimate.

Exports use the weather dataset that drove the prediction. Different datasets
or source runs produce separate NetCDF files in a ZIP; flights sharing one
source are combined. Weather grids are not horizontally or vertically regridded.
These model-box files use the app's documented model-field schema, independently
of the observational-style sonde schema.

The export uses the normalized saved dataset or direct native archive. If the
requested margin extends beyond that dataset, it is **explicitly clipped**. It
does not expand a normalized domain from unrelated cached GRIBs, fetch a newer
run, or invent missing fields. Download a larger weather domain before predicting
if you need a guaranteed full margin. Export progress reports the estimated size
and writing blocks; buffers are bounded to native row blocks. `max_export_mb`
defaults to 4096 MB (estimated uncompressed size, per box).

The app checks source receipts before and after export. If weather/DEM files
were removed or replaced, re-run the flight. Receipts use path, size and mtime,
not a cryptographic content hash. Avoid modifying source files while predicting.
Old v1.2 saved predictions lack these receipts: re-run them with v1.3 before
requesting sampled sonde/model-box exports. Existing track CSV/JSON exports do
not need resampling.

## Weather downloads, disk usage and cleanup

The ERA5 grid selector appears only for ERA5/ERA5T. IFS/GFS always submit their
0.25° product, even if you previously selected a coarser ERA5 grid. Download
start/end inputs use minute precision. Suggested starts round down and ends
round up, so their browser step constraints are valid. Launch/arrival inputs
still retain seconds. Backend weather requests accept second-bearing timestamps
and select covering native forecast hours.

Manage weather displays actual **server-side** paths and sizes for saved weather,
remote raw cache, predictions, model-box exports and terrain. With `start.sh`
and no custom configuration, Linux uses
`~/.local/share/balloon-predictor` (or `$XDG_DATA_HOME/balloon-predictor`).
IFS/GFS raw downloads are under `cache`, normalized datasets under `weather`.
A browser on another machine is showing paths on the predictor server.

Available cleanup actions have separate scopes:

| Action | Removed | Kept |
|---|---|---|
| Delete named weather dataset | Its normalized `.nc` and metadata | Shared raw cache, existing predictions and exports, native archives, terrain |
| Clear remote file cache | Cached remote GRIBs, request metadata and inactive partial files | Saved weather datasets, predictions, exports, native archives, terrain |
| Clear saved predictions & exports | Stored prediction results and generated sampled exports | Weather, raw cache, launch setups, terrain, native archives |

The UI shows dependent saved-prediction counts before dataset deletion. Removing
weather may prevent later sampled exports from those predictions. Already
written model-box files remain downloadable until exports are cleared. Active
jobs and response streams are protected by process-shared leases. Cleanup is
refused while data is in use. **Stop v1.2 or older servers before cleanup**: they
do not participate in the lease protocol. External editors/writers are also
outside this protocol.

**Refresh cached remote files** re-fetches matching remote request files when
downloading. It does not clear all caches or overwrite an existing named weather
dataset; choose a new dataset name.

## Desktop and mobile windows

- Map/Profile/Sounding toolbar buttons toggle the visible panel's minimized state.
- `+` maximizes a panel into the workspace; restore returns to the prior layout
  and panel visibility. Locks prevent accidental dragging/resizing.
- Unlock a window to drag its title bar, resize any edge/corner, or use title-bar
  arrow keys. The lower-right resize control also supports arrow keys.
- Dock Map and Profile and drag their divider to change the split ratio. Unlock
  both first; the separator supports Up/Down keys. **Dock** restores the docked
  placement and **Reset layout** restores the initial workspace.
- The Controls arrow is in the page header. On phones (≤760 px, or short touch-screen landscape), controls slide
  in from the left with a dismissible backdrop and Escape support. Main panels
  switch one at a time; setup controls never move underneath the profile. Job
  status is also visible above the main panel while controls are hidden.

## Verification

The release passes 82 backend tests, including coastal bridging/strict mode,
physical DEM landing, source-replacement detection, sonde consistency, ERA5 and
WRF field equality, full native exports, mixed-source ZIPs, time/domain selection,
cleanup dependencies, and lease protection across separate processes. The real
frontend JS passes DOM workflow tests including forecast grid/time validity,
maximise/restore, panel toggles, split resizing, edge gestures and mobile drawer.

A real public GLO-30 tile was downloaded and sampled. Previously downloaded real
2026-11-05 IFS/GFS GRIBs were run through v1.3 at a 1 m launch altitude through
20 km, including sonde and model-box export (IFS 14 levels; GFS 41 levels).
Those validation files and weather data are not bundled.

A real browser could not start in the build runtime, so visual desktop/Android
verification is **not claimed**. The included Playwright check can run locally
with `npm install`, `npx playwright install chromium`, and `npm run test:browser`.
DOM tests do not verify rendered corner clipping, actual touch behavior, or
layout appearance. Windows/PowerShell startup was reviewed, not executed here.
